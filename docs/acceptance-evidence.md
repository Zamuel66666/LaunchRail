The production dependency audit reported no known vulnerabilities.

Two real single-host lifecycle fault runs used dedicated synthetic projects and the healthy application from published source revision `8d441729a02e873e5e09b8e7eb8e53da544f6707`. Deleting the retained prior container produced a working recreated runtime and successful rollback (18 checks). Pausing the prior container produced a recorded `rollback_unhealthy` outcome and retained HTTP 200 from the current preview; a new command then successfully restored the prior release (21 checks). PostgreSQL retained the failed health attempt and both rollback outcomes. Follow-up Docker inventories found no remaining containers for either dedicated project after stop/cancellation cleanup. The saved reports explicitly record a dirty development worktree; these are development acceptance results, not exact-clean-release approval or controlled performance measurements.

Both fault scenarios were then repeated without code changes against clean published revision `a674b29c74764af34a1e7556407824b6bbdca3fd`: [missing-container raw report](acceptance/rollback-missing-a674b29.json) passed 19 checks, and [paused-container raw report](acceptance/rollback-paused-a674b29.json) passed 22. Both include a final assertion that the dedicated project's managed runtime inventory is empty, and both record `workingTreeClean: true`. The retained files are byte-for-byte copies of the command output, with SHA-256 digests `772f6cdd373f8bbb2458ddc2030f0738a7e4b9425de4f48049db1b348589921b` and `17b705efcc1c293e2deab6dd367463765c5fea21d89ed4ba0e2ca565430ef56c`, respectively. [CI for that exact revision](https://github.com/Zamuel66666/LaunchRail/actions/runs/38210098820) passed all three jobs, including real BuildKit, Docker, and Traefik acceptance. These functional results do not satisfy the remaining whole-release checklist or benchmark gates.

The production browser build connected to the real API and displayed the recorded rollback-failure guidance in deployment activity. Chromium axe-core WCAG 2 A/AA and WCAG 2.1 A/AA checks reported zero violations at the 390-pixel viewport, with no horizontal overflow. This is incremental regression evidence, not the complete keyboard/onboarding review.

Visual inspection also exposed landing-page success checkmarks leaking into every history entry, including failed deployments and failed health. The history-specific style now removes those decorative marks while retaining explicit outcome text and ordered chronology. The rebuilt browser reported `content: none` for failed, cancelled, stopped, active, and rolled-back history entries; desktop automated accessibility checks remained free of WCAG A/AA violations. This is not a five-second performance SLA.

## 2026-10-12 continuation

Verification added safe request-parser status handling, durable cancellation convergence, and a runtime-job budget correction so configured health grace is not cut short by the Docker command timeout. All 318 unit tests, 84 PostgreSQL/service tests, 18 HTTP integration tests, 15 queue/restart tests, and five restricted runtime/example tests passed locally. The webhook service suite covers real Redis wake-ups and retry after partial processing, including authorization and canary error boundaries. A rejected-first receipt regression failed before the recovery correction (both valid redeliveries returned HTTP 200 without processing); afterward concurrent signed redeliveries produced one HTTP 202 and one HTTP 200, one deployment, and a preserved rejection audit. The five webhook cases also use whitespace-preserving Unicode JSON to distinguish raw-byte signature verification from reserialization, and verify a late rejection cannot overwrite a recovered receipt.

The repeatable `pnpm acceptance:lifecycle` run passed healthy activation, failed-candidate preservation, replacement, rollback, queued cancellation, stop, and observed HTTP 200/404 preview changes without modifying the running worker during the run. Its worker profile used 10-second startup grace with a five-second Docker command timeout, proving grace consumes the total job budget instead. This is functional evidence, not a controlled performance benchmark.

The [operations guide](operations.md) records the private logical PostgreSQL backup/restore rehearsal and its explicit limitations. Clean-clone setup, complete interruption recovery, accessible first-run onboarding, controlled benchmarks, independent release review, and publication remain open.
